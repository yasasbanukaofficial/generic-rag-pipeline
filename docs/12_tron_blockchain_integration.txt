================================================================================
BATTLEX PLATFORM - TRON (TRX) BLOCKCHAIN INTEGRATION
================================================================================

1. ARCHITECTURE AND OBJECTIVE
--------------------------------------------------------------------------------
BATTLEX includes native cryptocurrency support for TRON (TRX), allowing players to
deposit and withdraw funds using native on-chain transactions without relying on
third-party custodial payment gateways.

Core Security Invariants:
- Hot Wallet Isolation: The server connects exclusively to a dedicated "Hot Wallet"
  for processing day-to-day player deposits and outgoing withdrawals.
- Zero Cold Wallet Key Exposure: The server NEVER stores, accepts, or touches the
  Cold Wallet private key (the startup script actively refuses to boot if `TRON_COLD_PRIVATE_KEY`
  is set). The cold wallet private key remains offline in the physical custody of the platform owner.
- Quorum Verification: High-security multi-node quorum support: queries can run against
  two independent TronGrid / Full-Node RPC providers to ensure agreement on chain state
  and transaction finality.


2. WALLET LINKING WORKFLOW (CRYPTOGRAPHIC PROOF OF KEY OWNERSHIP)
--------------------------------------------------------------------------------
To prevent address spoofing and ensure that deposits and withdrawals belong to the
actual player, users must link their TronLink wallet using a cryptographic challenge:

Step 1: Player opens Wallet -> TRON in the web app and clicks "Connect TronLink".
Step 2: Client requests a challenge nonce from the server:
        `POST /api/wallet/tron/link-challenge`
Step 3: Server generates a unique cryptographic nonce bound to the player's User UUID
        with a 5-minute expiration time.
Step 4: The TronLink browser extension prompts the player to sign the challenge text:
        `"BATTLEX Wallet Link: <nonce>"`
Step 5: Client submits the resulting hex signature:
        `POST /api/wallet/tron/link-confirm`
Step 6: Server verifies that:
        1. The signature recovers to the claimed base58check TRON address.
        2. The address is not already linked to another active player account.
Step 7: The TRON address is permanently bound to the user's account.


3. AUTOMATED DEPOSIT SCANNING & CREDIT
--------------------------------------------------------------------------------
BATTLEX operates a continuous background blockchain scanner that monitors the platform's
hot wallet address for incoming TRX transfers:

A. Scanning Cycle:
   - Polling Interval: Runs every 15 seconds (`TRON_POLL_INTERVAL`).
   - Query: Fetches finalized block transactions transferring native TRX to the hot address.

B. Deposit Verification Criteria:
   For a deposit to be credited, it must satisfy ALL of the following rules:
   1. Linked Address Match: The sender address (`from`) MUST match an existing, active,
      cryptographically linked user wallet. Deposits from unlinked addresses are flagged
      for manual investigation and NOT credited automatically.
   2. Range Check: The deposited TRX amount (in integer sun: 1 TRX = 1,000,000 sun)
      must be greater than or equal to `min_deposit_sun` and less than or equal to `max_deposit_sun`.
   3. Daily Limit Check: The deposit must not cause the player or the platform to exceed
      the configured UTC daily deposit limits (`user_daily_deposit_sun`, `global_daily_deposit_sun`).
   4. Solid Chain Finality: The transaction must be confirmed in a finalized/solidified block
      with zero risk of chain re-organization.

C. Coin Crediting:
   - The deposit amount in sun is converted to micro-coins using the active exchange rate
     at the exact block timestamp (`micro_coins_per_trx`):
       MicroCoins = (DepositSun * micro_coins_per_trx) / 1,000,000
   - An atomic double-entry ledger transaction credits the player's account:
       Debit:  `treasury`        (-MicroCoins)
       Credit: `player.available` (+MicroCoins)
   - Idempotency: Every deposit records the TRON transaction hash (`tx_hash`). Repeating
     a block scan or processing the same transaction twice is strictly prevented.


4. OUTBOUND WITHDRAWALS WORKFLOW
--------------------------------------------------------------------------------
Unlike deposits, outgoing TRX withdrawals are strictly protected by a two-admin
maker-checker approval process:

Step 1: Player Requests Withdrawal:
        - Player enters TRX withdrawal amount (minimum 2,000 coins + 200 coin flat fee).
        - The server locks the exchange rate at request time and calculates the exact
          payout in sun.
        - Coins are reserved in `withdraw_pending`:
            Debit:  `player.available`        (-2,200 coins)
            Credit: `player.withdraw_pending` (+2,200 coins)

Step 2: First Administrative Review (Maker):
        - Admin reviews the player's KYC status, risk flags, and gameplay history.
        - Admin approves the request (`first_approved` status).

Step 3: Second Administrative Approval & Broadcast (Checker):
        - A DIFFERENT administrator (super admin) with recent session TOTP executes the send.
        - Durable Intent: The server generates the raw transaction intent and stores it
          in `tron_transfers` table before signing.
        - Signing Lock: The server acquires an exclusive lock, signs the transaction using
          the hot wallet private key, and stores the signed raw bytes.
        - Broadcast: The transaction is broadcast to the TRON network.

Step 4: Chain Confirmation & Final Ledger Burn:
        - The background worker polls the transaction hash until finalized on-chain.
        - Once finalized:
            Debit:  `player.withdraw_pending` (-2,200 coins)
            Credit: `treasury`                (+2,000 coins burned)
            Credit: `fee_revenue`             (+200 coins platform fee)
        - The withdrawal is officially marked `paid`.

Failure & Uncertainty Handling:
- If the node returns an uncertain or timeout response, the system NEVER cancels or refunds
  the withdrawal automatically (to prevent double-spend attacks).
- The transfer remains locked in `pending` until solidified confirmation or verified failure.


5. HOT / COLD TREASURY MANAGEMENT AND SWEEPS
--------------------------------------------------------------------------------
To protect platform capital, the hot wallet maintains only the minimum working float
necessary to cover day-to-day operations:

A. Configured Float Parameters:
   - `hot_min_sun`: Minimum required balance. Dropping below triggers a critical alert.
   - `hot_target_sun`: Ideal operating balance.
   - `hot_max_sun`: Maximum allowed hot wallet balance.

B. Automated / Manual Sweeps to Cold Storage:
   - When the hot wallet balance exceeds `hot_max_sun`:
     * The system calculates the excess surplus above `hot_target_sun` plus in-flight payout commitments.
     * Initiates an on-chain transfer sending surplus TRX directly to the configured
       offline receive-only Cold Wallet address (`TRON_COLD_ADDRESS`).
     * The transaction is logged with masked address auditing.

C. Low Float Replenishment:
   - If hot wallet balance approaches `hot_min_sun`, operators receive an incident alert.
   - Platform owners manually transfer TRX from their offline cold storage wallet back to
     the hot address.
