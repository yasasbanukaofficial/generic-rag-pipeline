================================================================================
BATTLEX PLATFORM - MATCHMAKING, LOBBY AND GAME LIFECYCLE
================================================================================

1. GAME MODES AND STAKE TIERS
--------------------------------------------------------------------------------
BATTLEX supports two primary operational game modes:

A. Free Play Mode (Stake = 0):
   - Open to all registered players regardless of wallet balance.
   - Purpose: Casual competition, practice, game learning, and leaderboard rating.
   - Does not touch the financial ledger; zero fees charged.

B. Staked Play Mode:
   - Real-money coin stakes held in escrow.
   - Standardized fixed stake tiers per game:
     * Chess:    100 coins, 250 coins, 500 coins, 1,000 coins
     * Checkers: 100 coins, 250 coins, 500 coins
     * Ludo:     100 coins, 250 coins, 500 coins
   - Custom stakes are not permitted in general matchmaking to ensure deep liquidity pools.


2. MATCHMAKING QUEUE AND ELO MATCHING
--------------------------------------------------------------------------------
A. Queue Partitioning:
   - Matchmaking queues are partitioned by a composite queue key:
       Key = [game_type, seat_count, stake_tier]
   - Examples:
     * `[chess, 2, 0]` -> Free Chess queue
     * `[chess, 2, 250000000]` -> 250 Coin Chess queue
     * `[ludo, 4, 100000000]` -> 4-Player 100 Coin Ludo queue

B. Skill-Based Rating (Elo) Expansion:
   - When a player joins a queue, the matchmaker initially seeks an opponent within
     a tight Elo rating window (e.g. +/- 50 rating points).
   - The matchmaking clock ticks every second. As wait time increases, the rating window
     expands progressively (e.g. +/- 100 at 10s, +/- 200 at 20s, open matching at 30s).
   - If a queue timeout is reached without a match (e.g. 60 seconds), the player is notified
     and given the option to remain in queue or leave.


3. FRIENDS LOBBY & PRIVATE ROOMS
--------------------------------------------------------------------------------
- Players can bypass the public matchmaking queue by creating a Friends Lobby.
- The host selects the game, seat count (for Ludo: 2, 3, or 4 seats), and stake tier.
- The server generates an alphanumeric 6-character room invite code (e.g. "BX-7921").
- Other players join by entering the code or clicking a shared invite link.
- Seats are claimed as players enter. The host cannot start the game until all required
  seats are filled and all players have clicked "Ready".


4. SOFT BALANCE CHECK VS. ATOMIC LEDGER HOLD
--------------------------------------------------------------------------------
To protect players and prevent stalled rooms, BATTLEX uses a two-phase balance check:

A. Phase 1 - Soft Balance Check:
   - Executed at the moment a player attempts to join a matchmaking queue or lobby.
   - Verifies: `player.available >= stake_amount`.
   - If insufficient, the request is immediately rejected with a clear error prompt
     instructing the player to deposit or acquire coins from a merchant.

B. Phase 2 - Hard Atomic Ledger Hold:
   - Executed inside a single PostgreSQL database transaction at the exact moment
     a match is successfully formed (when all seats are filled).
   - Acquires a row lock on each player's account.
   - Debits `available` and credits `in_play`.
   - Underfunded Failure Handling: If a player spent coins between joining the queue
     and match formation, the hold fails for that player. The system automatically:
     1. Aborts the match without charging ANY player.
     2. Ejects the underfunded player with an error notification.
     3. Returns all funded players to the top of the matchmaking queue with their original
        entry timestamps preserved so they are matched with priority.


5. GAME ROOM LIFECYCLE AND WEBSOCKET PROTOCOL
--------------------------------------------------------------------------------
Once a match is created, a dedicated `Room` is spawned in memory on the server:

A. Room State Machine:
   `waiting` -> `active` -> `finished` (`won` / `checkmate` / `draw` / `resigned` / `forfeit`)

B. Client Connection Handshake:
   - Each player is issued a short-lived, single-use `game_token`.
   - Client connects via WebSocket to `/ws/games/{id}?token={game_token}`.
   - Server authenticates the token, assigns the client to their designated Seat ID,
     and broadcasts the initial `STATE` frame.

C. Action Dispatch & Turn Timers:
   - Current turn seat submits an `action` frame (e.g. `{"type": "move", "payload": {...}}`).
   - Server validates the action against the pure game engine (`engine.Validate`).
   - If valid, `engine.Apply` advances the game state.
   - Server restarts the turn timer and broadcasts the updated state to all connected room clients.

D. Turn Timeouts and Auto-Advance:
   - Each game has an authoritative turn timer (e.g. 30 seconds per turn).
   - If a player fails to submit a move before the turn timer expires:
     * The server calls `engine.AutoAdvance(state, seat)`.
     * For Ludo: If a roll has occurred, auto-moves a valid token, or passes turn if no move exists.
     * For Chess/Checkers: Applies a timeout strike; consecutive timeouts result in a game forfeit.

E. Disconnection Grace Period:
   - If a player's WebSocket disconnects mid-game (e.g. due to mobile network fluctuation),
     the room does NOT forfeit them immediately.
   - A disconnect grace timer starts (e.g. 45 to 60 seconds).
   - If the player reconnects within the grace window, their state is restored immediately.
   - If the grace period expires without reconnection, the disconnected player is marked
     as forfeited, and the game concludes with a win for the remaining player(s).


6. GAME COMPLETION AND DURABLE SETTLEMENT OUTBOX
--------------------------------------------------------------------------------
When a game reaches a terminal state (`is_game_over = true`):

A. Atomic Result Recording:
   - The game result (winner seat, final placements, reason, move history) and a durable
     `settlement_outbox` record are written in a single database transaction.
   - This ensures that a game can NEVER be marked as finished without queuing its financial settlement.

B. Outbox Settlement Worker:
   - An asynchronous background worker picks up unprocessed rows from `settlement_outbox`.
   - The worker invokes the economy domain to calculate the 90/10 pot split, affiliate unilevel,
     merchant pools, and director profit allocations.
   - Executes the double-entry financial settlement on the ledger.
   - Emits live WebSocket toast notices (`payout_received`, `reward_received`) to online players.
   - Marks the outbox item as processed.
   - Idempotency guarantees that even if the worker or server crashes mid-process, re-running
     settlement will never double-credit winners or double-deduct fees.


7. ABANDONED GAME SWEEPER (CRASH RECOVERY)
--------------------------------------------------------------------------------
- If a server process unexpectedly restarts while games are active, the `abandoned_sweeper`
  background job sweeps the database for rooms stuck in `active` status without recent heartbeat
  activity (default age: 10 minutes).
- Swept games are officially declared Voided.
- The voider refunds 100% of all player held stakes from `in_play` back to `available`.
- Zero fees are charged, ensuring players never lose money due to platform infrastructure faults.
